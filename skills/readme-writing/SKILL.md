# README の書き方

README を読む人はこのプロジェクトを知らない。
その前提を最後まで守ることが、この文書の要になる。

作業を始める前に `japanese-tech-writing` スキルを読み、その文章規範に従う。
このスキルは、その上に重ねる README 固有の規範を述べる。

## 読み手が知らないことを前提にする

読み手が持っているのは、目の前の README だけである。
変更の経緯、以前の構成、議論の過程、どの PR で何が変わったかを、読み手は何も知らない。

そのため次を書かない。

- 経緯そのもの（「以前はリポジトリに置いていたが、現在は〜」「〜に伴い変更された」）
- 経緯を知らないと意味の取れない記述（「これも D1 へ移した」の「これも」）
- 変更の理由づけ（「〜のため、この方式を採用した」）
- 課題番号、PR 番号、決定の日付

書くのは、いま何がどう動くかだけである。
経緯や判断の記録は `.decisions/` に、作業の計画は `.plans/` に置く。

**悪い例**：記事データはリポジトリからデータベースへ移行されたため、ビルド前にスナップショットの取得が必要になりました。
**良い例**：記事データはデータベースにあります。ビルドはその内容を取り出したスナップショットを読みます。

## 独立した主張を並べない

一文ずつ独立した事実を積み上げると、読み手は関係を自分で組み立てることになる。
論理的につながる内容は、接続の助詞や理由の表現で一つの文にまとめる。

まとめられるのは、因果、条件と帰結、手段と目的、限定と補足で結ばれた内容である。
無関係な事実を「〜で、〜します」と接続語だけでつなぐのは、まとめたことにならない。

**悪い例**（三つの独立した文が並ぶ）：
```
編集は 1.5 秒後に自動保存されます。
保存はデータベースへの改訂追加です。
そのため保存し忘れて失う下書きはありません。
```

**良い例**（因果でまとめる）：
```
保存は入力が止まってから 1.5 秒後に自動で実行されるため、保存の操作を忘れても編集内容は残ります。
```

## 既存の README に合わせる

書き始める前に README を通して読み、書き方の癖を掴む。
節ごとの分量、文末の形、専門用語をどこまで開いて書いているか、コマンドや設定値をどう示しているかを見る。

このリポジトリの README は、一文一行で、「〜します」「〜です」の平叙文で書かれている。
主張を煽らず、比喩を使わず、機能の説明と手順の提示に徹している。
追記した部分だけ語り口が変わると、読み手はそこで引っかかる。

## 書いたあとの点検

- この段落は、プロジェクトを知らない人が読んで意味が取れるか。
- 経緯や、以前の状態への言及が残っていないか。
- 隣り合う文が、まとめられる関係にありながら分かれていないか。
- 既存の節と語り口が揃っているか。
- 書いた手順を実際に実行できるか。手順を書いたなら、その通りに動かして確かめる。
